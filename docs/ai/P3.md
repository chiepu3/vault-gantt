# P3統合記録

作業先は `vault-gantt-ai-chat-initial` のみ。git操作なし。並行担当の新規handler・operation-catalogの登録行は変更していない。

## 実装

- `OperationService.inspectOutcome(previewId, context)` は read capability、Vault、保存時principal、取消・停止状態を確認する。別Vault/principalは `POLICY_DENIED`。保持していないIDは `NOT_FOUND`、認可済みで未実行の提案だけ `undefined`。結果は保存された全previewとの `validatePreviewOutcome` を通して複製を返す。MCPもこの認可付き参照を使用する。
- 工数mapと日別cellは同じ変更の二つの表現として検証する。beforeは元snapshot、両方のafterの一致、同一日の矛盾を検証し、二重適用しない。休日の変更には保存したsettings差分も含める。統合休日は保存したcalendarの和集合と照合する。
- チャット、Workbench、Gantt、承認一覧に OperationService / PreviewPort / ProjectionDetailPort / HumanApprovalPort / HistoryPort / UiPort / HumanUndoPort を渡す。ビューの実際の識別子と現在の表示状態を登録し、閉じると解除する。
- チャットでは共通カードを表示し、同じ提案の旧カードを二重表示しない。人間のカード承認と再プレビューの保存結果を次のチャット文脈へ記録する。projectionの全snapshotはモデルに再送しない。
- Ganttは共有focusのpreview overlayを使用する。承認一覧ビューと「AIの承認一覧を開く」コマンドを登録した。承認要求は要求元に合わせてチャットまたは承認一覧を開く。
- Undo実行は共通保存キュー内で履歴ID、先頭資格、ファイル内容を再確認する。結果をカード・各ビューへ反映する。
- MCPはdesktopかつ設定で有効なときだけ127.0.0.1で起動する。停止・再生成で、そのprincipalのpending提案をrevokedへ移す。applying・保存済み結果は取り消さない。遅れて起動が完了した場合もunload後にはlistenerを停止する。
- 設定画面に有効化、ポート適用、トークン生成・再生成・コピー、接続先、Vault instance ID、簡単な接続案内を追加した。トークン値は秘密ストレージまたはメモリのみ、plugin dataにはsecretIdだけ保存する。port変更は「適用」を押した時だけ再起動する。
- esbuildの外部参照に `node:*` を追加し、desktop用MCPの遅延ロードをbundleできるようにした。

## 追加契約

既存の型名・フィールドは削除・改名していない。

| 契約 | 追加内容 |
| --- | --- |
| `OperationPreviewV1` | optional `operationLabel`（表示用操作名）、optional `approvedEvent`（schemaVersion / kind=approved / eventId / previewId / occurredAt） |
| `PreviewEventV1` | approved / expired / revoked。承認はイベントで表し、既存の状態をapprovedに置き換えない |
| `PreviewPort` | optional `invalidate(previewId, "expired" \| "revoked")`、optional `subscribeEvents(listener)`。実PreviewStoreは両方を実装する。古いportは従来のrejectへfallbackする |
| preview status | `revoked` を追加。MCP status DTOも同じ失効を表す |
| `HumanUndoPort` | `undoEntry(entryId): Promise<void>`。人間用UIにだけ渡す |
| `PreviewUiHostPorts` | optional undoPort / operationService / projectionDetailPort / viewStatePort / viewId。既存hostも使用可能 |
| `ViewStateRegistrationPort` | 実ビューのread状態を登録・解除するport |
| read DTO | `EventReadResultV1`、`WeeklyReadResultV1`、`eventStateSchema`、`eventReadSchema`、`weeklyReadSchema`。key / title / dateまたは曜日・分数 / hours / edit revision / 件数・cursorを提供する |
| context query | `events.get`（eventKeys / dateRange / cursor / limit）、`weekly.get`（scheduleKeys / daysOfWeek / cursor / limit）。ContextIndexでも実装した |
| 管理値 | `ServiceStateV1`、`SERVICE_STATE_KEYS`、`serviceStateChangeSchema`、`service-state` effect。integration entityの独立actionで管理値の保存を表す |
| Gantt snapshot | optional `serviceState`。部分保存時も元beforeと保存済みeffectsから生成し、管理値とcalendarの整合を検証する |
| 操作のeffect種別 | T30 / S05 / S08へservice-state、S06 / S07へsettingsを追加 |

管理fieldは `lastAutoPriorityUpdate`、`ganttNationalHolidaysUpdatedAt`、`ganttNationalHolidays`、`ganttHolidays`。利用者編集のsettingキーや秘密情報とは別で、日付・時刻・日付配列の型を検証する。

並行担当のT30/S05等では、task更新・利用者設定の保存と別に、`{ kind: "integration", targetId: "priority-service" }` 等をentityにしたservice-state actionを作れる。各actionの成否を独立に表すこと。明示的なservice-state effectを投影する場合は、そのbefore/after管理値をsnapshotにも含める。管理値の保存自体のhandlerはこの工程では追加していない。

## 残課題

- 47操作（T30、D01〜D09、S05、S08、S18〜S21、S27、S35、V01〜V23、Q01〜Q06）は並行担当のhandlerの統合待ち。catalogの可用性・既存の登録口は変更していない。UiPortへのビュー登録はread状態を提供し、未接続のview requestは従来どおりUI_UNAVAILABLEとなる。
- 既存のGanttドラッグ、Workbench編集・新規作成は従来のOperationRegistry経路を維持し、OperationServiceと同じ保存キュー・HistoryManagerを共有する。非標準Markdownを扱う既存writerと新runtimeの保存拒否条件が異なるため、既存UIの全面移行は行っていない。
- 子の直接削除/日程付き追加、Daily編集、イベント・定例作業の既存UI保存、設定画面、休日・同期・自動優先度の旧経路は残る。これらの全面統合は別工程が必要。
- 実Obsidian UIシナリオの再実行は、既存ハーネスのchrome-sandbox確認が成立する環境で行う。
